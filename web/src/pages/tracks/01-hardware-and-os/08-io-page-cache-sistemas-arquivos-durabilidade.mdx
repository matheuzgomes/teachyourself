# Módulo 08: I/O, Page Cache, Sistemas de Arquivos e Durabilidade

Nos módulos anteriores desta trilha, investigamos a arquitetura interna do processador: desde a física dos transistores e portas lógicas no silício até a comutação de privilégios de hardware, paginação na MMU e concorrência multicore.
Ao longo dessa jornada, toda a computação operou sobre a premissa de memórias eletrônicas ultrarrápidas, cujos tempos de resposta são medidos em nanossegundos ou ciclos de clock.

Contudo, a memória RAM e as caches de hardware possuem uma característica fatal: elas são puramente voláteis.
Quando o fornecimento de energia elétrica é interrompido ou o servidor é reiniciado, todos os elétrons estabilizados nos circuitos de silício se dissipam instantaneamente, destruindo todo o estado computacional da máquina.

Para que uma transação bancária, uma mensagem de chat ou um registro de banco de dados sobreviva no tempo, o sistema precisa transferir esses bits para mídias físicas de armazenamento não-volátil (como unidades de estado sólido NVMe ou discos magnéticos).
Mas essa transferência impõe um abismo de latência sem precedentes:
Enquanto uma leitura de cache L1 consome 1 nanossegundo e um acesso à memória DRAM física leva cerca de 60 nanossegundos, uma operação de I/O em um SSD rápido consome entre 10 e 100 microssegundos, e um disco magnético tradicional pode levar 10 milissegundos.
Esse salto representa uma diferença de mais de cinco ordens de grandeza.

Neste módulo, você vai entender como o sistema operacional e o hardware resolvem esse abismo de desempenho:
Como a CPU se comunica com periféricos sem travar em loops de espera ativa através de Memory-Mapped I/O (MMIO) e Direct Memory Access (DMA), por que a chamada de sistema `write()` não garante persistência física e apenas grava dados no Page Cache da memória RAM, como primitivas de durabilidade como `fsync()`, `fdatasync()` e `O_DIRECT` orquestram o descarregamento de dados, e como sistemas de arquivos modernos evitam corrupção estrutural em quedas repentinas de energia através de Journaling e Write-Ahead Logging (WAL).

## 8.1 A Fronteira Física de I/O: Port I/O, MMIO e Controladores de DMA

No nível físico da placa-mãe, um processador não conversa apenas com os módulos de memória RAM.
Ele precisa trocar dados com placas de rede, controladoras NVMe, placas de vídeo e barramentos PCIe.
Para estabelecer essa comunicação sem adicionar fios elétricos dedicados para cada novo periférico inventado, a engenharia de computadores desenvolveu dois modelos de endereçamento de hardware:

1. **Port I/O Legado (Port-Mapped I/O):**
   Na arquitetura x86 original, a CPU disponibiliza um espaço de endereçamento separado de 16 bits exclusivo para portas de I/O (de `0x0000` a `0xFFFF`), acessado unicamente por instruções privilegiadas especiais: `in` e `out`.
   Nesse modelo, para ler um byte de um controlador de disco, a CPU executa uma instrução que bloqueia o núcleo até que o barramento responda.
   Esse mecanismo é lento, inflexível e incompatível com transferências volumosas de dados.

2. **Memory-Mapped I/O (MMIO):**
   Na arquitetura moderna, os registradores de controle e buffers dos dispositivos periféricos são mapeados diretamente no próprio espaço de endereçamento físico da memória.
   Quando a CPU executa uma instrução ordinária de movimentação como `movq %rax, (0xFED00000)`, o controlador de memória e o barramento PCIe interceptam o endereço físico e direcionam a carga diretamente para os registradores de circuito da placa controladora.
   Isso permite que o kernel configure placas de alta velocidade utilizando as instruções normais da ISA, sem depender de instruções especiais.

```text
+---------------------------------------------------------------+
|                      PROCESSADOR (CPU)                        |
|   Instruções: movq, addq | Sem polling contínuo da CPU        |
+---------------------------------------------------------------+
                               |
               Barramento PCIe / Sistema de Interconexão
                               |
       +-----------------------+-----------------------+
       |                                               |
       v                                               v
+-------------------------------+       +-------------------------------+
|     CONTROLADOR DMA (NVMe)    |       |       MEMÓRIA DRAM FÍSICA     |
| Transfere blocos diretamente  | =====>| Recebe molduras de dados      |
| para a RAM sem tocar na CPU   | (DMA) | diretamente na memória        |
+-------------------------------+       +-------------------------------+
       |
       +--- Dispara Interrupção de Hardware ao concluir
```

### O Controlador de DMA (Direct Memory Access)
Imagine o que aconteceria se a CPU tivesse que ler pessoalmente cada bloco de 4 KiB vindo de uma unidade NVMe:
Para transferir um arquivo de 1 GiB a partir de um SSD, o núcleo da CPU passaria bilhões de ciclos de clock em um laço de repetição, lendo 8 bytes por vez do barramento PCIe e gravando na RAM.
A máquina ficaria inteiramente congelada durante a leitura.

Para eliminar essa sobrecarga fatal, os computadores contemporâneos utilizam o **Acesso Direto à Memória (Direct Memory Access, ou DMA)**:
1. O driver do sistema operacional prepara um descritor de comando na memória RAM e escreve nos registradores MMIO do controlador NVMe, indicando o endereço físico de origem no disco, o endereço físico de destino na RAM e o número de blocos a serem lidos.
2. O processador fica livre imediatamente para escalonar e executar outros processos prontos da fila.
3. O controlador de DMA do dispositivo assume o barramento e transfere os blocos diretamente para a memória RAM física, sem intervenção do pipeline da CPU.
4. Ao concluir a transferência completa do bloco, o controlador de hardware emite uma **interrupção de hardware** para a CPU.
5. O tratador da interrupção no kernel intercepta o evento, acorda a thread solicitante que estava suspensa em repouso e disponibiliza os dados para o aplicativo.

## 8.2 O Ciclo de Vida da Escrita e o Page Cache do Kernel

Quando um desenvolvedor escreve uma rotina em C, Go ou Rust para gravar dados em um arquivo:
```c
FILE *f = fopen("dados.txt", "w");
fwrite(buffer, 1, 4096, f);
```
O que realmente acontece por baixo dos panos?
Existe uma crença ingênua de que a execução dessa linha de código força o cabeçote do disco a gravar bits na mídia imediatamente.
Na realidade física dos sistemas operacionais, os dados atravessam múltiplas camadas de buffering antes de atingirem o silício não-volátil.

O ciclo de vida de uma escrita atravessa quatro etapas estruturais:

1. **Buffer em Espaço de Usuário (Buffer da libc):**
   Funções como `fwrite()` ou buffers de escrita em linguagens de alto nível não invocam uma chamada de sistema a cada caractere emitido.
   A biblioteca padrão de C mantém um buffer interno em Ring 3 (geralmente de 4 KiB ou 8 KiB).
   A chamada `fwrite()` apenas acumula os bytes nessa memória privada da aplicação.
   Apenas quando esse buffer enche (ou quando a aplicação chama `fflush()`), a biblioteca executa a chamada de sistema `write()`.

2. **A Fronteira do Kernel e o Page Cache da RAM:**
   Quando a chamada de sistema `write()` é executada, a CPU eleva o privilégio para Ring 0 e entra no tratador do subsistema de arquivos do kernel.
   O kernel **não grava os dados no disco físico**.
   Em vez disso, ele localiza a moldura de página correspondente dentro do **Page Cache**: uma área da memória RAM física dedicada a espelhar blocos de arquivos do disco.
   O kernel copia os bytes do buffer de usuário para a página na RAM e marca essa moldura com o bit de modificação: ela se torna oficialmente uma **página suja (Dirty Page)**.
   Neste instante, a chamada de sistema `write()` retorna sucesso para a aplicação!

3. **A Fila do Escalonador de I/O (I/O Scheduler):**
   As páginas sujas permanecem na memória RAM volátil.
   Para maximizar a vazão e amortizar o custo de I/O aleatório, threads de segundo plano do kernel (conhecidas no Linux como `flusher threads` ou `kworker`) acordam periodicamente.
   Elas identificam páginas que estão sujas há mais de um limite configurado (por exemplo, 30 segundos no Linux sob `/proc/sys/vm/dirty_expire_centisecs`), agrupam essas escritas contíguas em estruturas de requisição de blocos (`struct bio` / `struct request`) e as posicionam na fila do escalonador de I/O do driver de disco.

4. **O Controlador e as Caches Internas do Hardware:**
   O driver de dispositivo despacha a fila de requisições para a controladora do SSD ou disco magnético via barramento PCIe/NVMe.
   Porém, mesmo os dispositivos de armazenamento físicos contêm suas próprias caches voláteis de escrita em DRAM embutidas no circuito da controladora.
   Se a controladora apenas gravar os blocos em sua cache interna e a energia cair, os dados ainda serão irremediavelmente perdidos.

```text
[ Aplicação de Usuário (Ring 3) ]
             |
       fwrite() / fflush()
             v
[ Buffer da Biblioteca libc (RAM) ]
             |
       syscall write()
             v
[ KERNEL: PAGE CACHE (RAM Volátil) ]  <--- Dados marcados como DIRTY
             |                             Retorno imediato de write()!
       Flusher threads assíncronas
             v
[ Fila do Escalonador de Blocos ]
             |
       Transferência DMA via PCIe
             v
[ Cache Volátil Interna do SSD/Disco ]
             |
       Descarga física
             v
[ Mídia Não-Volátil (Células Flash NAND) ]  <--- Persistência Real
```

## 8.3 O Mito do `write()` Seguro: Por que `write()` Não Persiste Dados

A mecânica de buffering descrita na seção anterior revela uma das fontes mais comuns de perda de dados em sistemas de software:
**A confirmação com sucesso da chamada de sistema `write()` não oferece nenhuma garantia de persistência física.**

Considere o seguinte cenário de produção em um sistema transacional:
1. Uma aplicação bancária desconta cem reais de uma conta e chama `write()` para registrar a transação no arquivo de log contábil.
2. O kernel recebe os dados, aloca uma moldura no Page Cache da RAM, marca a página como `dirty` e retorna o valor retornado `4096` indicando sucesso.
3. A aplicação interpreta o retorno, informa ao cliente que a transação foi concluída com segurança e fecha a conexão.
4. Dois segundos depois, um disjuntor do data center desarma e a máquina perde a energia elétrica.

Como o kernel aguarda o ciclo assíncrono das threads de descarregamento para transferir páginas sujas para a controladora, os dados da transação bancária ainda residiam exclusivamente nos transistores voláteis da memória RAM.
Com a interrupção da corrente elétrica, a memória RAM física é zerada.
Quando o servidor religar, o arquivo de log no disco estará no estado em que se encontrava antes da operação: o registro da transação simplesmente desapareceu, violando a propriedade de Durabilidade do modelo transacional.

Por que os sistemas operacionais foram projetados dessa forma aparentemente perigosa?
Por uma razão imperativa de desempenho:
Se a chamada `write()` fosse síncrona por padrão, cada chamada de escrita forçaria a CPU a esperar centenas de microssegundos ou milissegundos pela conclusão do disco.
Servidores web, compiladores e bancos de dados veriam sua capacidade de processamento desabar em mais de noventa e nove por cento.
O Page Cache atua como um escudo amortecedor essencial que transforma centenas de pequenas escritas esparsas em descargas contíguas e ordenadas de alta velocidade.

## 8.4 Primitivas de Durabilidade: `fsync()`, `fdatasync()` e `O_DIRECT`

Quando uma aplicação desenvolve um software de armazenamento crítico: como os motores de bancos de dados PostgreSQL, MySQL, SQLite ou mensagerias como Kafka: ela não pode depender da boa vontade do descarregamento assíncrono do sistema operacional.
Ela necessita de primitivas explícitas de persistência garantida.

O padrão POSIX disponibiliza três mecanismos fundamentais para controlar essa fronteira de durabilidade:

### 1. A Chamada `fsync()` (Sincronização Completa de Dados e Metadados)
A chamada de sistema `fsync(int fd)` suspende o fluxo da aplicação e instrui o kernel do sistema operacional a:
1. Identificar todas as páginas sujas pertencentes àquele descritor de arquivo dentro do Page Cache da RAM;
2. Enfileirar essas molduras imediatamente no escalonador de blocos;
3. Atualizar e sincronizar todos os metadados do arquivo em disco (como o nó de índice / *inode*, o carimbo temporal de modificação `mtime` e o tamanho do arquivo);
4. Emitir um comando de barreira de escrita (*Flush Cache* / *Write Barrier*) diretamente para o circuito do SSD ou disco rígido, forçando a controladora a descarregar suas caches internas voláteis para as células flash não-voláteis;
5. Retornar para a aplicação somente após a confirmação física de que os bits foram gravados na mídia permanente.

O custo de `fsync()` é substancial: enquanto um `write()` no Page Cache leva poucas centenas de nanossegundos, um `fsync()` exige tipicamente de 1 a 10 milissegundos em mídias convencionais.

### 2. A Chamada `fdatasync()` (Sincronização Otimizada de Dados)
Em muitos cenários práticos, o arquivo apenas teve seu conteúdo interno alterado, sem alteração no tamanho total do arquivo que impeça sua leitura íntegra.
A chamada `fdatasync(int fd)` introduz uma otimização crítica de desempenho:
Ela força o descarregamento de todas as páginas sujas de dados do arquivo, mas **omite a gravação de metadados não-essenciais** (como a atualização contínua do horário de acesso ou modificação no *inode*).
Ela só grava metadados se a alteração for estritamente necessária para que uma futura leitura localize os novos blocos físicos (por exemplo, se o tamanho do arquivo tiver aumentado).
Essa distinção economiza uma operação de I/O adicional no cabeçote do disco ou no bloco de metadados do sistema de arquivos, acelerando significativamente sistemas transacionais.

### 3. A Flag `O_DIRECT` (Bypass do Page Cache)
Ao abrir um arquivo com a flag `open("dados.db", O_RDWR | O_DIRECT)`, a aplicação estabelece um contrato radical com o sistema operacional:
O kernel é instruído a contornar integralmente o Page Cache para todas as leituras e escritas naquele arquivo.
As transferências de dados ocorrem diretamente entre os buffers de memória alocados pelo usuário em Ring 3 e o controlador de armazenamento físico através de DMA.

* **Vantagens de `O_DIRECT`:**
  Grandes sistemas de banco de dados (como PostgreSQL, Oracle e RocksDB) possuem seus próprios algoritmos sofisticados de gerenciamento de cache de blocos em espaço de usuário (*Buffer Pool*), perfeitamente ajustados à semântica das consultas SQL.
  Utilizar o Page Cache do kernel criaria o problema da **dupla paginação (Double Buffering)**: os mesmos blocos de dados estariam duplicados na RAM, ocupando espaço tanto no pool da aplicação quanto no Page Cache do sistema operacional, disputando recursos de memória física.
* **Restrições e Armadilhas de `O_DIRECT`:**
  1. **Alinhamento Estrito de Hardware:** O uso de `O_DIRECT` exige que todos os ponteiros de memória do usuário, deslocamentos de arquivo (*offsets*) e tamanhos de escrita sejam rigorosamente alinhados aos limites dos blocos físicos do dispositivo de armazenamento (tipicamente alinhamentos de 4096 bytes).
  2. **`O_DIRECT` Não Equivale a `O_SYNC`:** Existe uma concepção errônea perigosa de que contornar o Page Cache torna a escrita imediatamente imune a quedas de energia. No hardware real, a transferência DMA envia os dados diretamente para a cache volátil de escrita do controlador de armazenamento (DRAM do SSD ou disco). Sem a invocação explícita de `fsync()`, `fdatasync()` ou o uso da flag `O_SYNC`, uma queda repentina de energia apagará os blocos retidos na cache volátil do dispositivo.
  3. **A Armadilha do Diretório Pai em Criações e Renomeações:** Ao criar um arquivo novo ou renomear um arquivo existente (como no padrão de escrita atômica via arquivo temporário), chamar `fsync()` no descritor de arquivo do novo arquivo garante apenas os blocos de dados e o *inode* do arquivo. A entrada de diretório (*dentry*) que vincula o nome do arquivo ao seu número de *inode* continua residindo no Page Cache do diretório pai! Se a energia falhar antes que o comando `fsync()` sincronize o diretório pai, o arquivo simplesmente não será encontrado na árvore de diretórios após a reinicialização. Para atingir persistência completa e durável na criação de arquivos, a aplicação deve abrir o diretório pai e executar `fsync(dir_fd)` no descritor do diretório pai.

## 8.5 Consistência Contra Quedas (*Crash Consistency*) e Journaling

Para além da durabilidade do conteúdo de um arquivo individual, existe um problema ainda mais complexo e ameaçador para sistemas de arquivos: a **consistência estrutural contra quedas de energia (Crash Consistency)**.

Considere o que ocorre internamente em um sistema de arquivos como ext4 ou XFS quando você anexa um bloco de 4 KiB ao final de um arquivo existente:
O sistema operacional precisa executar três gravações distintas na mídia:
1. **O Bloco de Dados ($D$):** Os 4096 bytes de conteúdo recém-gerados pela aplicação;
2. **O Nó de Índice Inode ($I$):** A estrutura de metadados que guarda o tamanho do arquivo, o ponteiro de bloco para o novo endereço físico e o horário de modificação;
3. **O Bitmap de Alocação de Blocos ($B$):** O mapa de bits que registra quais blocos do disco estão ocupados e quais estão livres.

Como esses três blocos residem em locais físicos distintos do disco, eles não podem ser gravados atomicamente em um único ciclo de barramento.
Se uma queda súbita de energia ocorrer no meio dessa sequência, o sistema de arquivos pode cair em estados de inconsistência catastróficos:

* **Cenário de Falha 1 (Apenas o Inode foi gravado, mas o Bloco de Dados não):**
  O inode aponta para um endereço físico no disco onde os dados nunca chegaram a ser gravados.
  Ao reiniciar, o arquivo conterá lixo aleatório que residia previamente naquele setor físico, abrindo vazamento de dados ou corrupção silenciosa.
* **Cenário de Falha 2 (Apenas o Bloco de Dados foi gravado, mas o Inode e o Bitmap não):**
  Os dados estão no disco, mas nenhum arquivo sabe onde eles estão e o bitmap marca o espaço como livre.
  Uma alocação posterior irá sobrescrever esses bytes.
* **Cenário de Falha 3 (Inode gravado apontando para o bloco, mas o Bitmap não foi atualizado):**
  O arquivo aponta para o bloco, mas o sistema de arquivos acha que o bloco continua desocupado.
  Quando outro arquivo for criado, o kernel alocará o mesmíssimo bloco para o novo arquivo, corrompendo ambos os arquivos simultaneamente.

```text
DESAFIO DA CONSISTÊNCIA ESTRUTURAL:
Para anexar um bloco, três estruturas precisam ser gravadas:
[ Bloco de Dados D ] + [ Inode I ] + [ Bitmap de Blocos B ]

Se a energia cair no meio do caminho:
- Queda após D: Espaço órfão.
- Queda após I: Inode aponta para lixo magnético.
- Queda após B: Espaço ocupado sem dono.
```

### A Solução Clássica: FSCK (File System Consistency Checker)
Nos primórdios dos sistemas Unix, a solução consistia em reiniciar a máquina em modo de emergência e executar o utilitário `fsck`.
O programa realizava uma varredura completa por todo o disco rígido: percorrendo milhões de inodes, tabelas de diretórios e blocos de dados para conferir se cada ponteiro possuía um bloco correspondente no bitmap.
Em discos de centenas de gigabytes ou terabytes, o `fsck` demorava horas ou até dias para concluir, mantendo servidores críticos fora do ar durante todo o processo.

### A Solução Moderna: Journaling e Write-Ahead Logging (WAL)
Para resolver esse problema de forma determinística e permitir recuperação de falhas em frações de segundo, os sistemas de arquivos contemporâneos (como ext4 com JBD2, XFS e NTFS) incorporaram a técnica de **Journaling**, baseada nos princípios fundamentais de *Write-Ahead Logging (WAL)* desenvolvidos por Mohan e Jim Gray:

Em vez de alterar diretamente as estruturas originais do sistema de arquivos no disco, o sistema adota um protocolo em duas fases rigorosamente sequenciadas:

1. **Fase 1: Registro da Intenção no Diário (Journal Write):**
   O kernel reúne todas as alterações pendentes (o bloco de dados, o novo inode e o novo bitmap) em uma estrutura transacional coesa denominada transação.
   Ele grava essa transação de forma sequencial em uma área reservada e contígua do disco, denominada **Journal (Diário)**.
   Ele grava um bloco de início de transação (*Tx Begin*) e todos os blocos alterados.
2. **Barreira de Escrita (Write Barrier):**
   O kernel emite uma barreira de escrita para garantir que todas as estruturas da transação estejam fisicamente gravadas na mídia do diário antes de prosseguir.
3. **O Bloco de Confirmação (Commit Block):**
   Após a confirmação da barreira, o kernel grava um bloco especial de confirmação: o **Commit Block** (*Tx End*).
   No instante em que o commit block é confirmado na mídia física, a transação é considerada oficialmente atômica e imutável.
4. **Fase 2: Gravação Definitiva no Local Original (Checkpointing):**
   Com a transação gravada com segurança no diário, o kernel pode copiar as estruturas com calma para as suas posições definitivas no sistema de arquivos.
   Assim que a cópia definitiva termina, o espaço daquela transação no diário é liberado para reutilização.

### O Mecanismo de Recuperação Rápida em Reinicializações
Se a máquina sofrer uma queda súbita de energia:
* **Caso a queda ocorra ANTES da gravação do Commit Block:**
  O sistema operacional inspeciona o diário durante o boot e identifica uma transação incompleta (sem bloco de commit).
  Ele simplesmente descarta os blocos incompletos do diário.
  O sistema de arquivos permanece no estado íntegro anterior, sem nenhuma inconsistência estrutural.
* **Caso a queda ocorra APÓS o Commit Block, mas antes do Checkpointing:**
  O sistema operacional detecta que a transação está completamente confirmada no diário.
  Ele simplesmente reexecuta a operação (*Redo*), copiando os blocos do diário para suas posições definitivas.
  A recuperação conclui em poucos milissegundos, sem necessidade de varrer o disco inteiro.

## 8.6 Síntese de Arquitetura, Latências e Heurísticas de Produção

A tabela a seguir resume as ordens de magnitude típicas das operações de entrada e saída, ilustrando o abismo físico de latência que separa as memórias eletrônicas da persistência em disco:

| Operação de I/O | Mecanismo Subjacente | Latência Típica | Custo Relativo (Base: Ciclo de CPU) |
| :--- | :--- | :---: | :---: |
| **Leitura de Cache L1** | SRAM interna do núcleo da CPU | ~1 ns | 1 ciclo de clock |
| **Leitura de Memória DRAM** | Barramento DDR físico externo | ~60 ns | ~200 ciclos |
| **Escrita no Page Cache (`write()`)** | Cópia entre buffers na memória RAM | ~500 ns a 1 µs | ~1.500 a 3.000 ciclos |
| **Leitura de SSD NVMe (DMA)** | Barramento PCIe e células Flash NAND | ~10 a 50 µs | ~30.000 a 150.000 ciclos |
| **Chamada `fdatasync()` em SSD** | Esvaziamento de Page Cache e comando flush | ~1 a 3 ms | ~3.000.000 a 9.000.000 ciclos |
| **Leitura Aleatória em Disco Magnético** | Rotação mecânica e deslocamento do braço | ~10 ms | ~30.000.000 ciclos |

---

### Quatro Heurísticas Invariantes de Engenharia para Sistemas de Armazenamento

1. **Nunca assuma durabilidade com base em `write()` bem-sucedido:**
   Se a integridade do seu dado não pode ser perdida em caso de reinicialização ou falha de energia, invoque explicitamente `fsync()` ou `fdatasync()`. Em bancos de dados de produção, utilize bibliotecas com suporte formal a WAL e commits coordenados.
2. **Utilize Group Commit para amortizar o custo de sincronizações físicas:**
   Invocar `fsync()` para cada evento individual limita o rendimento do sistema a poucas centenas de operações por segundo. Sistemas de alta performance agrupam transações de múltiplas threads concorrentes em uma única chamada física de `fsync()`, multiplicando a vazão por ordens de grandeza.
3. **Avalie o uso de `O_DIRECT` apenas se você mantiver um Buffer Pool próprio:**
   Para aplicações normais, o Page Cache do kernel é muito mais rápido e eficiente do que tentar gerenciar memória manualmente. Adote `O_DIRECT` apenas em motores de banco de dados e sistemas analíticos especializados que implementem algoritmos dedicados de substituição de páginas.
4. **Monitore o volume de páginas sujas no Linux com ferramentas reais:**
   Evite que o acúmulo descontrolado de dados não-persistidos provoque congelamentos no sistema durante o descarregamento em lote. Inspecione regularmente a quantidade de páginas pendentes através dos comandos:
   ```bash
   cat /proc/vmstat | grep nr_dirty
   cat /proc/meminfo | grep Dirty
   ```
